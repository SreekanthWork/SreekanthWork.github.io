Broker API Onboarding and Trading Signal Verification

A product and data initiative that connected third-party brokers to the core signal engine, verified every execution against the intended trade, and made the path from alert to order faster and more reliable.

Map broker onboarding

Broker setup involved several manual steps, and users could drop out before reaching live auto-execution.

  • Documented the data and status changes needed between the app, broker authentication and the core signal engine.
  • Worked with engineering on Alice Blue and Angel One flows.
  • Captured failure states and activation checks so support and QA could test them.

Build a verification trail

Execution records were difficult to reconcile against the signals that triggered them.

  • Matched daily signal alerts to broker-side execution logs with PostgreSQL.
  • Exposed a feed delay associated with a mismatch in leaderboard values.
  • Supported the correction of the verification flow.

  • Measured movement from live notification to the execution screen in Mixpanel and Amplitude.

    reconcile_pnl.sqlPostgreSQL
    

    SELECT s.signal_id,
       s.published_pnl AS platform_pnl,
       e.pnl AS broker_pnl,
       e.pnl - s.published_pnl AS delta,
       p.ingested_at - e.executed_at AS feed_lag
FROM signals s
JOIN broker_executions e ON e.signal_id = s.signal_id
JOIN pnl_feed p ON p.execution_id = e.execution_id
WHERE s.trade_date = CURRENT_DATE
  AND e.pnl <> s.published_pnl
ORDER BY feed_lag DESC;

    Match and tolerance rule
    Requirement FR-07.2
    
            
    
              
    Verified when
    Signal and execution identifiers, instrument, quantity and side all match.
    
              
    Flagged when
    A price or timestamp difference exceeds the agreed tolerance.
    
              
    Excluded when
    An execution is unmatched or incomplete. It stays out of verified P&L until resolved.
